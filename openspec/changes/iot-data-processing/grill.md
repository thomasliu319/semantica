## B. 阻塞题（理解业务，决定怎么杀）

### B1. 这一步之后，业务 Y 是什么？

数据只能支撑它能支撑的问题。利用率有日表；故障预测缺可靠故障标签；主轴没有历史。

| 选项 | 含义 | 若选错 |
|---|---|---|
| `oee` | 稼动 / 停机结构诊断 | 后面会按 OEE 洗日历日，低稼动样本会大量保留 |
| `pdm` | 预测性维护 / 报警升级 | 必须先定义「故障」；当前报警多为 M01/其它 |
| `type_compare` | T-600 vs T-V856S 对比 | 两机型必须分池或显式分层，不能混成一个分布 |
| `fleet_health` | 客户现场健康度看板 | 客户泄漏、同厂多机要当聚类而不是独立样本 |
| `clean_only` | 本步不定 Y，只出干净表 | 清洗门槛只能用数据质量，不能用「对模型有没有用」 |

推荐默认：`clean_only`（导图下一步才是特征工程）。  
若选 `pdm`，必须再定义故障：`BreakDownTime>0` / 报警未解决 / 无法定义。

### B2. 分析原子粒度？

| 选项 | 对齐的接口 | 不适合 |
|---|---|---|
| `device_day` | 运行状态就是日 | 程序段内部的工况 |
| `device_month` | 月趋势已有 | 会抹掉日停机 |
| `event` | 报警 + 程序时间戳 | 没有日利用率主表 |
| `hybrid` | 日事实表 + 事件从表 | 工作量最大，最不容易用错 |

推荐默认：`hybrid`（`device_day` 主表，`alarm_event` / `program_cycle` 从表）。

### B3. 「宁肯错杀」杀到哪一层？

188 台「接口齐全」≠「这段时间在干活」。3 月 187 台运行秒数为 0。

| 选项 | 大约留下 | 杀掉的东西 |
|---|---|---|
| `keep_188` | 188 台 × 184 日 | 几乎不杀，3 月全是停机日 |
| `drop_idle_device_month` | 有运行的设备-月 | 冷启动月；3 月基本消失 |
| `drop_zero_run_device` | 187 台 | 仅 `182606055` |
| `active_only` | 运行小时 ≥ p25（约 96h） | 约 47 台低稼动 |

推荐默认：`drop_idle_device_month`（台还在，空月丢掉）。  
这是导图「让数据纯」和「还要不要 3 月」的交点。

### B4. 两种机型怎么处理？

T-V856S 报警均值 1142，T-600 仅 138；运行小时均值 424 vs 320。混池会让立加报警淹没钻攻。

| 选项 | 含义 |
|---|---|
| `split` | 两套清洗/两套表，机型不混 |
| `pooled_flag` | 一张表，强制保留 `EquipTypeCode` |
| `v856s_only` | 只要立加 |
| `t600_only` | 只要钻攻 |

推荐默认：`pooled_flag`（本步清洗一套规则，机型当维度；特征工程再决定是否分模型）。

### B5. 日历窗口？

| 选项 | 含义 |
|---|---|
| `mar_aug` | 3–8 月全留 |
| `drop_mar` | 丢掉几乎全零的 3 月 |
| `may_aug` | 从 5 月有产量的月份起 |
| `run_days_only` | 只留 `RunTimeSec>0` 的设备-日 |

推荐默认：`drop_mar` + 仍输出完整日历到 `dq_report`，便于审计。

## D. 可默认题（防污染 / 交付）

### D1. 剩余 12 台？

推荐：`exclude`。`172609583` 无台账身份；其余缺程序或报警，不满足完备定义。

### D2. 哪些源禁止当设备时序？

推荐锁定（建议本步直接写进 spec，不再问第二次）：

- 禁止：客户级开机合计。
- 禁止：主轴快照当 3–8 月历史。
- 禁止：未按 `EquipCode` 过滤的程序行。
- 允许：主轴只进 `device_dim` 的「拉取时刻状态」，并标注 `as_of`。

### D3. 以后若做模型，切分单位？

推荐：`by_company`（106 客户；伟迈特 15 台同分布，按设备随机切会泄漏）。  
本步若 `clean_only`，只在维度表保留 `CompanyId`，不切 train/test。

### D4. 清洗产物？

推荐：`parquet` + `dq_report.json`，路径 `datasets/processed/iot_mar_aug_2026/`。  
JSON 原始层只读，不改。

### D5. 报警时长用哪一列？

推荐：解析 `DurationDetail`；`Duration` 与详情冲突则丢该字段，不丢整条报警。

## E. 增补阻塞题（轴/伺服 · 维护记录）

幻灯片五类信号：CNC 运行、报警/事件、轴/伺服、环境/辅机、维护记录。  
现采只有前两类的**历史**。PdM/MES 文档没有跟随误差、冷却液、液压、振动、保养工单、换刀台账接口。

### E1. 轴/伺服怎么进本步？

现有 `GetEquipSpindleWithFeedData` 是拉取时刻快照（约 09-16）。193 台完备里 192 台有 `ResultData`：XYZ 负载约 90% 有值，电流 100%，刀位 70%；**跟随误差无字段；温度/转速反馈 `CurrentTemperature`/`CurrentRotate` 全空；A/C 轴负载全空**。不能当 4–8 月轴伺服时序。

| 选项 | 含义 | 若选错 |
|---|---|---|
| `snapshot_keep` | 保留 `spindle_asof`（XYZ 负载、电流、刀位、转速、进给），`as_of` 强制非空，禁止 join `device_day` | 后面仍不能做轴劣化曲线 |
| `uncover` | 本步不把轴/伺服当分析信号，只在 `dq_report.uncovered_signals` 记缺口 | 快照表可仍写，但不进特征清单 |
| `wait_api` | 停清洗，先要历史轴/伺服接口 | 数据处理整步暂停 |
| `join_day` | 把快照摊到 4–8 月每一天 | 直接造假时序，禁止 |

推荐默认：`snapshot_keep`（有什么标什么，宁肯错杀也不编历史）。

### E2. 维护记录用什么？

没有保养/换刀/维修主数据接口。报警 117,566 条里：`ProcessStatus` 几乎全是「已解决」（仅 2 条未解决），`ProcessTime` 全有；`Resolvent`/`Repairtor`/`Level` 全空；**`ProcessDept` 与 `AbnoContent` 99.99% 相同**（不是部门，是报警正文）。刀位只在主轴快照。报警正文里会出现「刀臂正在换刀」「ATC维修模式」，那是报警文本不是工单。

| 选项 | 含义 | 若选错 |
|---|---|---|
| `alarm_proxy` | 用报警当维修代理：`process_status`/`process_time`/`is_shutdown`/`is_guarantee`；正文含换刀/维修作标签列 | 会把几乎全部已解决报警当成维修完成 |
| `breakdown_day` | 只用 `device_day.breakdown_time_sec>0` 当故障维修日 | 没有保养、没有换刀 |
| `uncover` | 本步不做维护表，缺口写入 `dq_report` | 特征工程看不到维修 |
| `wait_cmms` | 停下来要 CMMS/保养/换刀接口 | 整步暂停 |

推荐默认：`uncover`（宁肯错杀：没有台账就不当有维护记录）。

环境/辅机（冷却液、液压、振动）当前 **零字段**，不单开一题，默认与 `uncover` 相同，记入 `uncovered_signals`。
